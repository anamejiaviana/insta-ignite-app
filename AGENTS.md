# Project rules

- Every edge function that calls the AI Gateway must be wrapped with `guarded()` from `supabase/functions/_shared/guard.ts` — it verifies the JWT cryptographically (401 otherwise), reserves quota atomically via `reserve_quota` before the AI call and refunds via `release_quota` on failure, so cost abuse is impossible from the client.
- Quota RPCs (`reserve_quota`, `release_quota`, `increment_usage`, `get_text_limit`) are service_role-only; per-plan limit values live in the SQL functions `get_image_limit` / `get_text_limit`, so changing limits is a migration, not a code change.
- New files in the `post-images` bucket go under `{userId}/...` (client uploads and edge-function outputs); storage RLS checks the first folder, and legacy root-level paths are kept untouched so old URLs keep working.
- Image-source rules (default source, which sources spend image quota) live in `src/lib/contentRules.ts` with tests in `contentRules.test.ts` (run with `bun test ./src/lib`), so UI flows never decide AI usage on their own.
- Editorial guides live in `editorial_guides` (one row per client, RLS by owner + client ownership). Only the `approved` manual reaches generators, as a capped text from `buildGuideContext` merged into the `tone` field via `aiTone` (`src/lib/editorialGuide.ts`), so it works with already-deployed functions and never overwrites the client's own fields.
- Plan access is decided by `user_plans.status` (`trial`/`active`/`expired`/`comp`/`legacy`) inside `reserve_quota`; trials use TOTAL counters (`month='trial'`) plus a shared daily image cap row (sentinel user `00000000-…`, `trial_images_daily`). A trigger blocks non-backend changes to status/trial dates, so only service_role can grant `active`. Client mirrors expiry in `isTrialExpired` (`src/hooks/useUserPlan.ts`, tested in `src/lib/trial.test.ts`).
- Business count is enforced by the `enforce_business_limit` BEFORE INSERT trigger on `clients` (advisory lock per owner) using `get_business_limit` (status/plan based; legacy keeps its stored limit); the client mirror `businessLimitFor` is display-only, so the limit can't be bypassed from the browser.
- Billing data lives in `subscriptions` / `billing_events` (read own, write service_role only; `billing_events.event_id` is the idempotency key), so only a verified webhook can ever change plan status.
